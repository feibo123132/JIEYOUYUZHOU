## 点歌台：修复"点了歌却看不到"（按路演地点归类 + 去向透明）

用户需求：点"点歌"后歌曲没有出现在点歌榜"已点"里，希望按最近路演地点归类后能看到。

### 根因链（三层都查过）
1. 后端 `votes:increment` 原本只按 `latestRoadshowLocation(owner)`（站主 workspace 的路演记录按 date/updatedAt 取最新）归类；若路演记录缺失/地点字段与 `ROADSHOW_LOCATION_KEYS` 不一致（校验允许任意文本），则投票**只进总榜**，在任意地点 tab 下都看不到。
2. 前端 `requestSong` 提交后按"当前查看的 rankingLocation"刷新数据——归类地点与查看地点错位时歌曲"消失"，且无任何提示。
3. **关键遗漏**：`cloudfunctions/songRequestSync/validation.js` 的 `votes:increment` 分支只返回 `{ action, songId }`，会**丢弃前端传入的 `location` 字段**——若想用前端指定归类地点，必须放行。

### 改动（4 个文件）
- `cloudfunctions/songRequestSync/validation.js`：`votes:increment` 返回加上 `...optionalRankingLocation(event.location)`（非法地点仍抛 INVALID_LOCATION），使地点字段可穿透校验。
- `cloudfunctions/songRequestSync/index.js`：`votes:increment` 优先使用 `request.location`（若合法），否则回退 `latestRoadshowLocation(owner)`；返回值新增 `location: location || null` 供前端提示。
- `src/components/SongRequest/songRequestCloud.ts`：`incrementCloudVote(songId, location?)` 签名扩展，返回 `{ count, location: RoadshowLocation | null }`。
- `src/components/SongRequest/SongRequestStation.tsx`：
  - `requestSong`：不传隐性地地点（点歌按钮在歌手列表、无地点上下文，后端按最近路演归类最符合用户心智）；成功后按 `incrementResult.location` 明确 toast：归入某地点 / 无路演只计总榜；失败回滚+提示不变。
  - "已点"空态文案增强：总榜空 → 提示刚点的歌可在其他地点或看右上角提示；非总榜空 → 提示切回总榜查看。
  - 顺带删除合并功能后遗留的死代码 `handleRemoveSong`（实际删除路径是编辑模式里的 `handleDeleteSongById`）。

### 验证
- Node 实测 validation.js：带地点通过、无地点通过、非法地点/非法 songId 拒绝。
- `tsc -b --noEmit` 通过；`tests/songOrder.test.ts` 5/5；ESLint 仅剩仓库既有 no-empty/no-explicit-any；4 文件 UTF-8 完好。

### 备注
- 设计决策：投票归类保持"后端权威"（最近路演地点），前端只在无路演时告知"计入总榜"，避免用排行榜页残留的 rankingLocation 状态做归类依据产生新错位。

## 点歌台：根治"点了歌看不到"（后端写入可靠性 + 前端状态分离）

用户反馈：点了歌看到归入地点提示，但切换到对应地点后仍为空（"你骗我？！！"）。

### 根因链（深挖后）
1. **后端写入不可靠**：`incrementVote` 使用 `command.inc(1)` + 点号路径 `locationCounts.${locationKey}` 做 `update`。CloudBase/Firestore SDK 对点号路径嵌套字段的原子递增支持不确定，可能导致 `locationCounts` 未正确创建/更新，地点分榜永远为空。
2. **前端状态被覆盖**：`votes` state 在点歌后被 `pullCloudVoteState(location)` 直接覆盖为地点分榜数据。若分榜为空（由原因1导致），`ranking` 直接为空。
3. **地点筛选从未真正生效**：`rankSongsByVotes(songs, counts)` 只有两参数，从不接收地点——前端地点按钮 UI 只是改变了 `rankingLocation` state，但 `ranking` 的计算从未按地点过滤。

### 改动
- `cloudfunctions/songRequestSync/index.js`：`incrementVote` 彻底重写——改用 `get` + `set`（先读文档取当前 `count` 和 `locationCounts`，再整文档 `set` 回写），不再依赖 `command.inc(1)` 和点号路径，确保 `locationCounts` 嵌套对象一定正确创建/更新；返回新 `count`。
- `src/components/SongRequest/SongRequestStation.tsx`：
  - 新增 `locationVotes` state（`VoteCounts`），专存地点分榜数据。
  - `votes` state 职责锁定为"总榜数据"——组件挂载 useEffect 始终拉总榜到 `votes`，`rankingLocation` 变化 useEffect 额外拉地点分榜到 `locationVotes`。
  - `requestSong`：成功后拉总榜更新 `votes`（确保 ranking 永不为空），同时若当前查看具体地点则刷新 `locationVotes`。
  - `finishAllRequestedSongs`：同理，唱完后刷新总榜到 `votes`、地点分榜到 `locationVotes`。
  - `ranking` useMemo：根据 `rankingLocation` 选择 `votes`（总榜）或 `locationVotes`（分榜）传入 `rankSongsByVotes`，地点筛选终于真正生效。

### 验证
- `tsc -b --noEmit` 通过。
- `tests/songOrder.test.ts` 5/5 通过。
- ESLint 仅剩仓库既有问题，无新增。
