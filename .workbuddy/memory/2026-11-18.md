## 标记旗标可拖拽微调位置（15:09）

**需求**：AUDIO TRIM 波形上的 M 标记定位不准，希望按住旗标能左右拖动、多次微调。

**实现（`AudioTrimDialog.tsx`）**
- `markers` 的 `time` 就是身份，拖动时**不能逐帧写回**（key 一变就重设指针捕获、拖动会断）。改为本地 `markerDrag = { time, draft, moved }`：拖动期间只更新 draft 用来画，`key` 保持原时间，松手才 `setMarkers` 排序写入。
- 时间换算必须用 `wrapRef` 的矩形 + `timeAtX(x, width)`（旗标只有 28px，不能拿它当坐标系）。
- 边界：夹在「当前视图 ∩ 保留片段」`[max(start, viewStart), min(end, viewEnd)]`，否则拖出视图旗标会消失、拖进被裁片段会被 `timeline.contains` 过滤掉。
- 防重合：落点若与其他标记同点（差 < 1ms 逐次让 1ms），因为 `normalizeAudioMarkers` 用 time 作 Map 键，同点重载会被合并掉。
- 交互分流：`pointerup` 里 `moved ? 提交 : setEditingMarkerTime(time)`；`onClick` 只处理 `event.detail === 0`（键盘 Enter/Space），鼠标点击不会重复触发。
- 视觉：`cursor-grab / cursor-grabbing`、`touch-none`（iPad 上拖旗标不滚页）、拖动时旗标加深并在下方显示毫秒级时间标签（贴边时改 `left-0/right-0` 防裁切）；帮助行加「拖动蓝色旗标可左右微调标记位置」。

**验证（真实浏览器 CDP 拖拽，临时 harness 用完已删）**
- 拖 140px：0:01.000 → 0:01.711，chips 同步更新，编辑器未被误开。
- 边界：拖到最左 0:00.000、最右 0:06.000（无负值/越界）。
- 轻点不移动：编辑器正常打开。
- 落到另一条标记上：变成 0:01.011，两条都在。
- `tsc -b --force` 通过、eslint 0 error（仅既有两条 warning）。

**已知限制**：放大后只能在当前视图内拖（拖到边缘会停住），要移动更远需先缩小视图或拖概览。`vite build` 的 dist 清理会被 safe-delete shim 拦（报 trash-failed），需用 `--outDir` 换目录构建，或用 `find -type f -exec rm -f` 逐文件删。

## 补充：片段评论 + 两个增益的撤销（15:5x-16:0x 收尾）

**现状盘点（上一轮已做完的部分）**

**本轮补完的两个真缺口**
1. `keydown` 里原来「焦点在 INPUT/TEXTAREA 就 return」，导致**拖完增益滑块焦点停在 range 上，Ctrl+Z 完全失灵**（正是用户要的场景）。改为 `isTextEntryTarget()`：只让 text/search/email/url/tel/password/textarea/contentEditable 走原生，range/number 等仍归弹窗撤销。

**顺手补的防回归**：撤销放开后要避免抢控件自己的键——新增 `isFormControlTarget()`，方向键 / Delete·Backspace / Home·End 在 INPUT·SELECT·TEXTAREA 上不再接管（滑块能用键盘微调、数字框退格只改数字）。

## 修复：只评了合唱指数的歌不出现在合唱榜

**症状**：简单爱（合唱 91）、雨爱（合唱 92）在详情页有合唱指数、也传了录音，但合唱榜查不到；录音榜正常。

**根因**（用户猜得对）：`rankSongsByPracticeMatch`（songRecords.ts）在源头就 `.filter(score !== null)` —— 没有**匹配指数**的歌根本不进 `personalRanking` 数组，而合唱/狂扫/板凳三个分榜都是在这同一份数组里排序的，所以整首消失。录音榜走 `collectRecordingScores`，与练习记录无关，因此不受影响。

**修法**
- `rankSongsByPracticeMatch` 改为 `flatMap`：只要有任一指数（匹配/合唱/狂扫/板凳）就收录，匹配指数缺省记 `score: 0`；一个指数都没评（只写了感想）不收录。
- `SongRequestStation` 分榜各自按本项指数过滤：`chorusScore !== null` / `strumScore !== null` / `stoolScore !== null`；练习榜仍是 `score > 0`。这样只评合唱的歌不会带着空分蹲在狂扫榜底部。
- 云函数那边本来就对（`hasAnyScore` 四指数联合、`score: count ? ... : 0`），`parsePublicPracticeRanking` 也保留 0 分项，两边对齐。

**测试**：`tests/practiceOptionalIndex.test.ts` 原断言「只评其它指数 → ranking 为 []」改为断言 `score === 0` 且指数分保留，另加「一个指数都没评不占名额」「分榜只收评过本项指数的歌」。指数相关 5 个测试文件 44/44 通过，`tsc -b --force` 通过；`tests/songRequest.test.ts` 20 条失败均为历史遗留（旧文案/平均分 vs 最高分），与本次无关。
