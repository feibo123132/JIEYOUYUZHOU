## 标记旗标可拖拽微调位置（15:09）

**需求**：AUDIO TRIM 波形上的 M 标记定位不准，希望按住旗标能左右拖动、多次微调。

**实现（`AudioTrimDialog.tsx`）**
- `markers` 的 `time` 就是身份，拖动时**不能逐帧写回**（key 一变就重设指针捕获、拖动会断）。改为本地 `markerDrag = { time, draft, moved }`：拖动期间只更新 draft 用来画，`key` 保持原时间，松手才 `setMarkers` 排序写入。
- 时间换算必须用 `wrapRef` 的矩形 + `timeAtX(x, width)`（旗标只有 28px，不能拿它当坐标系）。
- 边界：夹在「当前视图 ∩ 保留片段」`[max(start, viewStart), min(end, viewEnd)]`，否则拖出视图旗标会消失、拖进被裁片段会被 `timeline.contains` 过滤掉。
- 防重合：落点若与其他标记同点（差 < 1ms 逐次让 1ms），因为 `normalizeAudioMarkers` 用 time 作 Map 键，同点重载会被合并掉。
- 交互分流：`pointerup` 里 `moved ? 提交 : setEditingMarkerTime(time)`；`onClick` 只处理 `event.detail === 0`（键盘 Enter/Space），鼠标点击不会重复触发。
- 视觉：`cursor-grab / cursor-grabbing`、`touch-none`（iPad 上拖旗标不滚页）、拖动时旗标加深并在下方显示毫秒级时间标签（贴边时改 `left-0/right-0` 防裁切）；帮助行加「拖动蓝色旗标可左右微调标记位置」。

## 修复：只评了合唱指数的歌不出现在合唱榜

**症状**：简单爱（合唱 91）、雨爱（合唱 92）在详情页有合唱指数、也传了录音，但合唱榜查不到；录音榜正常。

**根因**（用户猜得对）：`rankSongsByPracticeMatch`（songRecords.ts）在源头就 `.filter(score !== null)` —— 没有**匹配指数**的歌根本不进 `personalRanking` 数组，而合唱/狂扫/板凳三个分榜都是在这同一份数组里排序的，所以整首消失。录音榜走 `collectRecordingScores`，与练习记录无关，因此不受影响。

**修法**
- `rankSongsByPracticeMatch` 改为 `flatMap`：只要有任一指数（匹配/合唱/狂扫/板凳）就收录，匹配指数缺省记 `score: 0`；一个指数都没评（只写了感想）不收录。
- `SongRequestStation` 分榜各自按本项指数过滤：`chorusScore !== null` / `strumScore !== null` / `stoolScore !== null`；练习榜仍是 `score > 0`。这样只评合唱的歌不会带着空分蹲在狂扫榜底部。
- 云函数那边本来就对（`hasAnyScore` 四指数联合、`score: count ? ... : 0`），`parsePublicPracticeRanking` 也保留 0 分项，两边对齐。

**测试**：`tests/practiceOptionalIndex.test.ts` 原断言「只评其它指数 → ranking 为 []」改为断言 `score === 0` 且指数分保留，另加「一个指数都没评不占名额」「分榜只收评过本项指数的歌」。指数相关 5 个测试文件 44/44 通过，`tsc -b --force` 通过；`tests/songRequest.test.ts` 20 条失败均为历史遗留（旧文案/平均分 vs 最高分），与本次无关。

## 录音播放：切维度不断播 + 息屏/后台继续播

**问题 1**：录音在播时从「谱子」切到「练习」，`{activeJournal === 'score' && (...)}` 把整个谱子面板连同 `<SongRecordings>` 卸载，cleanup 里的 `stopPlayback` 直接掐掉声音。
**修法**：谱子面板改为**常驻挂载、只隐藏**（`aria-hidden` + `hidden` class），组件不卸载 → 播放不受切换影响；另外在 `data-journal-toolbar` 里加了一个「正在播放录音 · 停止」胶囊（调用新增的 `SongRecordingsHandle.stopPlayback`），人在练习维度也能掐掉。

**问题 2（手机息屏断播）**：原来解码成功就走 Web Audio（`AudioBufferSourceNode` + GainNode）。移动端页面进后台/息屏时 `AudioContext` 会被系统挂起，声音立即没了；而且没有 Media Session，系统根本不把它当播放器。
**修法（`SongRecordingPanel.tsx`）**
- 默认改成**媒体元素 `<audio>` 播放**（只有它能被系统当播放器接管）：`playsinline`、`preload=auto`；裁剪的删除段靠 **rAF 逐帧 `probePlayback` 追帧跳过**（前台 ~16ms，听不出），后台 rAF 停了由 `timeupdate`（~250ms）兜，回到前台由 `visibilitychange` 重启追帧。
- **Media Session**：`applyMediaSession()` 写 metadata（录音名 + 歌名·歌手）与 `playbackState`，并绑 play/pause/stop 动作 → 锁屏/通知栏有封面、有控制。
- **iOS 手势解锁**：点播放时先同步 `unlockAudioElement()`（`SILENT_WAV` data URI + `play()`），再换 src，否则 iOS 把后续 `play()` 当自动播放拦掉。
- 只有 `hasRecordingGain(recording.gain)` 的录音仍走 Web Audio（`<audio>` 的 volume 上限 1，抬不动 +dB），这类录音息屏仍可能被系统暂停（已知取舍）。
- 顺带：`finishPlayback`/`stopPlayback` 会 cancel 追帧、清 media session；`probePlayback` 抽到 `recordingPlayback.ts`（并给该文件的导入补 `.ts` 后缀，node --test 才 import 得动）。

**顺手修掉一个编译错误**：`SongRecordingPanel.tsx` 的上传配额守卫引用了不存在的 `item.deletedAt` 且没导入 `RECORDING_CLOUD_LIMIT`（不是本次改的代码，疑似另一处编辑残留）；改成 `recordingsRef.current.length >= RECORDING_CLOUD_LIMIT` 并补导入。

**验证**：`tsc -b --force` 通过；`vite build` 通过（57.8s）；新增 `tests/recordingBackgroundPlayback.test.ts` 6/6；音频相关 19/19；`tests/songRequest.test.ts` 仍 20 条历史遗留失败（无新增）。同时把 `tests/songRequest.test.ts` 里断言「`activeJournal === 'score' && <section data-song-score-panel`」改成断言常驻挂载的新结构。

### 追加上限到 2000（存安要求「有备无患」）

上限直接改成 `SONG_RECORDING_LIMIT = 2000`，同时补了两道以前没有的保险：

- **元数据体积闸**：`SONG_RECORDING_META_MAX_BYTES = 4_000_000`。`recordings:pull` 会把整批元数据塞进一次返回，云函数返回上限约 6MB，条数没到顶但标记/留言特别多时照样会撑爆——超了抛 `RECORDING_STORAGE_FULL`（已进白名单，前端提示「先删旧录音」），而不是让所有设备一起拉不到列表。只拦「新增」，编辑/评分老录音不受影响。
- **本机缓存裁剪**：`RECORDING_CACHE_LIMIT = 400` + `trimRecordingCache`。2000 段 JSON 约 2.2MB，Chrome 的 localStorage 按 UTF-16 计字节约 4.4MB，离 5MB 配额只剩一线；裁剪规则是「未同步的全留、其余按 updatedAt 取最新」，裁掉的老记录由云端 pull 补回，`pendingSync` 一条都不会被挤掉。
- 实测数据：线上工作台整档 365KB（34 段录音占 38KB，其余是路演等），单段录音元数据约 1.1KB → 2000 段约 2.6MB，落在 4MB 闸内；COS 侧按 4MB/段估算 2000 段约 8GB。

**验证**：`tsc -b --noEmit` 通过；`vite build` 通过（14.5s）；云函数测试 44/44（上限用例改成从源码正则读 `SONG_RECORDING_LIMIT` 并断言 ≥2000）；`recordingScore.test.ts` 新增缓存裁剪用例 11/11；已重新 `tcb fn code update` 并回读线上代码确认 `SONG_RECORDING_LIMIT = 2000`、`SONG_RECORDING_META_MAX_BYTES = 4_000_000`、`RECORDING_STORAGE_FULL` 都在。
