## 排查：点歌台「云端暂时未连接」/ 匿名登录失败

**现象**：页面能打开，但点歌台底部提示「云端暂时未连接」，登录弹窗提示「云端暂时没有回应」；Console 大量 `Failed to load resource: net::ERR_CONNECTION_CLOSED`（指向 `jieyou-3gr01mvob9ad92de-*.tcloudbaseapp.com`），`匿名登录失败 Failed to fetch`。

**结论：不是云环境故障，是本地 Clash 全局代理把腾讯云域名也代理到境外节点。**

诊断证据：
- 直连测试（`curl --noproxy "*"`）：`<env>.service.tcloudbase.com` → 403、`<env>.tcloudbaseapp.com` → 418，均 0.2s 可达。
- 走 Clash `http://127.0.0.1:7890`：同一批域名 **HTTP 000 连接失败**，与浏览器 `ERR_CONNECTION_CLOSED` 完全一致。
- 系统代理已开：`HKCU\...\Internet Settings` → `ProxyEnable=1`、`ProxyServer=127.0.0.1:7890`。
- Clash 进程：`D:\Clash.for.Windows-0.20.16-ikuuu\`（iKuuu 定制版），数据目录 `data/`。
- Clash API `http://127.0.0.1:54121/configs` 返回 **`"mode":"global"`**；`data/profiles/list.yml` 的 `index: 12` 指向 `1762871428185.yml`，其中同样写死 `mode: global`。
- 该 profile 规则本身是健康的：`GEOIP,CN,🇨🇳 国内网站` + 「国内网站」组当前为 `DIRECT`，只要切到 rule 模式腾讯云即直连。

**修复**：Clash → 模式从「全局」切到「规则」（或加 `DOMAIN-SUFFIX,tcloudbaseapp.com,DIRECT` 等规则），然后刷新页面。

**通用排查套路**（可复用）：
1. 浏览器报 `ERR_CONNECTION_CLOSED` 时，先区分「服务端挂了」还是「本地链路被劫」。
2. 用 `curl --noproxy "*"` 直连 + `curl --proxy 127.0.0.1:<port>` 走代理做 A/B 对照。
3. 读系统代理注册表 `ProxyEnable` / `ProxyServer`。
4. 直接查 Clash 控制 API `/configs` 看 `mode`——`global` 是这类问题的头号嫌疑。

## 排查：「编辑谱子」提示谱页无法载入 / console 报 CORS

**现象**：缩略图正常显示，点「编辑谱子」后编辑器空白，提示「谱页无法载入编辑器。请检查网络连接」；console 重复报 `Access to fetch at 'https://6a69-<env>-1386199420.tcb.qcloud.la/song-request-scores/...jpg?sign=...&t=...' from origin 'http://localhost:5174' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header`，URL 带 `#score-retry=N`。

**机制**：`ScorePageEditor.tsx` 用 `fetch(source)` 读图再 `drawImage` 到 canvas（保存要导出像素），而 `<img src>`（缩略图/翻谱器）不检查 CORS，所以出现「图能看、编辑器打不开」的割裂。

**实测结论（服务端 CORS 是好的）**：
- `curl --noproxy` 对 `tcb.qcloud.la` 加 `Origin: http://localhost:5174` / `5173` → 403 响应**带** `Access-Control-Allow-Origin`（精确回显，非通配）。
- `Origin: http://example.com` / `https://jieyou.example.org` / `http://127.0.0.1:5174` → **不带** CORS 头。说明白名单精确匹配 `localhost:5173/5174`，不认 `127.0.0.1`。
- 加 `Referer` / `Sec-Fetch-*` / Chrome UA 模拟浏览器请求，CORS 头依然在。
- 系统代理 `ProxyEnable=0`（已关），走 Clash 7890 时该域名 SSL 握手失败，但浏览器当前不走系统代理。

→ 服务端没问题，故障落在浏览器侧（扩展拦截 / 缓存了旧的无头响应 / 页面所在 origin 与白名单不一致）。

**代码改动**：`ScorePageEditor.tsx` 捕获 `TypeError` 判定为 CORS 拦截并输出独立提示与 `console.error`（打印 blockedByCors/source/error），不再一律归因为「网络连接」；非 200 时错误码带 HTTP 状态（`FETCH_FAILED_<status>`）。`tsc` 通过，无测试依赖该文案。

**待验证**：无痕窗口、DevTools 勾 Disable cache + 硬刷新、确认地址栏为 `localhost`（非 `127.0.0.1`）。若仍失败，可考虑云函数代理图片（base64 返回）作兜底。

**验证**：`tsc -p tsconfig.json --noEmit` 0 错误；`songRequestSyncFunction` 36/36、`practiceChorusStars` 5/5、`singingMoods` 2/2、`accountSongLibrary` 6/6、谱子组 14/14 全绿；`songRequest.test.ts` 16 个失败均为改动前既存（avg vs max、文案 aria-label 等源头断言脱节），修改前 17（含本次引入 1 个）→ 修改后 16，无新增。

## 兜底方案落地：`scorePages:read` 云函数代理读谱

**背景**：`编辑谱子` 的 `fetch` 被浏览器按跨域规则拦下（`<img>` 不走跨域所以页面看谱正常，编辑器要 `fetch → blob → drawImage` 取像素就挂）。无痕窗、硬刷新均无效，改为云函数代理兜底。

**服务端**（`cloudfunctions/songRequestSync`）
- `validation.js`：`ACTIONS` 加 `scorePages:read`；把谱页 fileID 正则抽成常量 `SONG_SCORE_PAGE_FILE_ID`（`cloud://…/song-request-scores/<64hex>/<64hex>/<uuid>.jpg`），`validateSongScore` 与代理接口共用，**杜绝借接口读其它云端文件**；代理必须带 alias+password（非公开动作）。
- `index.js`：常量 `SCORE_PAGE_PROXY_MAX_BYTES = 3_500_000`（云函数返回上限约 6MB，base64 放大 1/3，正好卡在谱页上传上限）；`PUBLIC_ERRORS` 加 `SCORE_DOWNLOAD_FAILED` / `SCORE_PAGE_TOO_LARGE`；store 加 `downloadSongScorePage(fileID)`（复用已在 `copySongScorePageFile` 用过的 `app.downloadFile`，超限抛 `SCORE_PAGE_TOO_LARGE`）；在**认证之后**分发，返回 `{ ok, contentType, base64 }`。
- 坑：store 对象是 `createHandler({...})` 的内联字面量，**内部没有 `store` 这个绑定**，所以方法里不能写 `store.logError?.()`（会 ReferenceError），只能直接 `console.error`。

**前端**
- `songRequestCloud.ts`：新增 `readScorePageViaProxy(credentials, fileId): Promise<Blob>`，用 `fetch(\`data:image/jpeg;base64,${...}\`)` 交给浏览器原生解码（比手写 atob + 逐字节循环快）。
- `ScorePageEditor.tsx`：新增 `loadFallback?: () => Promise<Blob>`。加载策略改为「先直连，非 2xx 或 `TypeError` 一律走兜底」——**顺带修掉签名地址过期导致的裂图**（代理按 fileID 取，与签名无关）。兜底回调存进 `fallbackRef` 而非依赖数组，否则上层每次渲染换新箭头函数会让谱页重载、批注被清空。错误文案按 `SCORE_PAGE_TOO_LARGE` / `SCORE_DOWNLOAD_FAILED` / CORS 分档。
- `ScoreViewer.tsx` 新增 `loadPageFallback(index)` 透传；`SongDetailPanel.tsx` 用 `session + score.pages[index]`（原始 `cloud://` fileID，**不是**解析后的签名地址）提供 `loadScorePageFallback`。

**验证**：`tsc -b --noEmit` 0 错误；`songRequestSyncFunction` 36→39（新增 3 个：只允许读谱页 / 正常代取 base64 / 未登记拒绝 + 超大报错）；`songRequest.test.ts + practiceChorusStars + publicSongScores` 122 项中 16 项失败，与改动前基线一致，无新增。

### 追加：录音本地保存 + 多端同步（照抄谱子范式）

**问题**：录音既不在本地留存，也不能电脑/iPad 互通。

**根因**：① 上传前先 `decodeAudioData`，某些格式解不出就直接抛错，一个字节都没存；② 云存储是 PRIVATE 桶，客户端直传没写权限 → 403；③ 元数据只进 localStorage，换设备全靠重传。

**前端（SongRecordingPanel.tsx）**
- `upload()` 改为「本地优先」三段式：`readAudioDuration()`（`<audio>` 元数据读时长，宽容）→ `putRecordingBlob` 写 IndexedDB + `commitWith` 落列表（`pendingSync: true`）→ 再 `void syncRecording(id, recording)` 异步上云。解码失败只影响裁剪面板，不影响保存。
- 新增 `syncRecording(id, seed?)`：本机无 fileID 就取 Blob → `uploadSongRecordingFile` → 拿 fileID **先落本机**（`pendingSync: true`），再 `saveCloudSongRecording` 写元数据；失败保留本机并标记，供重试。`syncingRef` 防并发重入。
- `commitWith()` 改为**以 `recordingsRef` 为唯一真相源同步计算**（`updater(ref.current)` 后立刻回写 ref 再 setState）——原实现依赖 setState 函数式更新，异步流程里读 ref 会拿到旧值，导致上传后 fileID 丢失。
- `saveTrim()` 改为并到 `recordingsRef.current` 的最新一条，避免裁剪期间上传完成把 `fileID` 冲掉。
- 云端拉取合并：`local.pendingSync` 为真时**保住本机版本**，防止刚裁好的区间被云端旧值覆盖。
- 自动补传：`session?.alias` 变化时把上次没传成功的（`pendingSync && !fileID`）自动续传一次；另外「同步 N 段到云端」按钮 + 每行「重试同步」。
